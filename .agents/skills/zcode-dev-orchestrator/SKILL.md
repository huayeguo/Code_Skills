# 开发任务编排与交接（ZCode 版）

主代理负责目标、方案、集成、验证和连续性，也直接完成适合自己做的工作。用户不必指定代理数量或角色。本版本只面向 ZCode：子代理按预置机队路由，模型档位固化在机队卡片上，派发时不可传。

## 入口与需求审查

1. 识别用户期望的结果、提出的实现办法、验收标准和明确限制。利用已提供的项目背景，不重复询问。缺少信息时先查现有资料；只有会实质改变产品结果、兼容承诺或成本边界的缺口才要求用户决定。
2. 在真实项目内读取适用的项目指令和已有目标、状态、索引。沿用现有文档路径；无同等文档时采用 `docs/ai/PROJECT.md`、`docs/ai/STATE.md` 和 `docs/ai/MAP.md`。不要为了一个小修复建立整套文档；没有仓库时说明只能提供计划或代码草案。
3. 用事实区分“问题存在”与“拟议办法能解决问题”。对有实质影响的需求，简短给出目标、判断、关键证据或待验证假设、建议行动。合理需求直接推进；调查可解决的不确定性先做有界调查；发现反证时重新判断，不为延续已投入工作而继续错误路线。
4. 原因不充分时不要迎合，也不要为体现批判性强行反对。只有存在实质收益时才扩展一个更好的替代方向；说明它的代价。改变明确的产品目标前请用户决定，工程判断在已授权范围内自行处理。
5. 实际开发开始时，读取 [会话检查与交接](references/session-checkpoints.md)。确定本次可验收任务单元，并记录必要基线与检查点。

## 运行模式

- **实现模式**：用户要求修改、修复、重构、迁移或交付可验证行为时，按完整流程审查、分工、实施和验证。
- **只读审阅模式**：用户要求项目状态、代码路径、风险或资料核实时，不修改文件、不启动服务、不把调查结论当作已验证功能；主代理先建立调查任务图，再按独立路径和当前可用并发槽位安排一个或多批只读子代理。
- **非项目讨论**：解释概念、翻译或泛泛讨论不运行编排流程，也不为了展示 skill 创建子代理。

## 先决定是否需要子代理

技能被用于实际开发时，请按以下条件使用子代理，不要求用户逐次分配角色：

- 至少能指出一个具体价值：独立工作可并行；调查将产生大量无关中间材料，适合隔离；重要变更需要独立证据审查。
- 必须能够写明具体问题或产出、必要上下文、读写边界、验收或停止条件。
- 协调、重复读取和集成成本与任务规模相称。主代理等待结果时有独立工作可以推进；若只能完全等待且收益不足，直接执行。
- 先画出最小任务图：哪些工作已就绪且互不依赖，哪些必须等待共享接口、调查结论或前一批结果。仅把前者并行化。

输出一行足够，例如“本次由主代理直接处理：定位明确，分工收益很小”，或“第一批并行调查调用方、迁移兼容性和现有测试，再由主代理确定接口并实施”。只读审阅任务同样说明“主代理直接审阅”或“按任务图分两批调查”；不为普通问答生成任务编排报告。

适用方式：

| 情况 | 执行方式 |
|---|---|
| 已定位的局部修复、机械且可核对的修改 | 主代理直接处理 |
| 项目状态汇报、资料核实或局部只读审阅 | 主代理直接处理；有独立调查路径时按任务图和可用并发槽位分批使用只读代理 |
| 范围不清，但可提出有边界的调查问题 | 必要时派只读调查代理；主代理同步处理另一独立问题 |
| 多模块边界明确、共享接口已确定 | 按文件/模块所有权并行实现 |
| 共享接口仍在变化、同一核心文件需反复修改 | 先确定接口，或串行修改；可以并行只读调查 |
| 迁移、兼容、权限或架构变更的错误代价较高 | 主代理实施或整合，必要时独立审查实际证据 |

并行数量不是固定常数。每一批的数量取“已就绪且互不依赖的任务数、当前可用并发槽位、可安全整合的结果数”三者中最小的值；若独立任务多于可用槽位，按最能解除后续依赖的顺序分批运行。每个代理都必须有独立产出，不能把同一问题换个名字重复派发。主代理可以在等待期间推进不重叠工作，并在每批结果返回后重新计算下一批；共享接口未定、同一文件写入或结论互相依赖时保持串行。始终服从当前环境限制。禁止子代理自行递归扩编；有新调查需求时返回主代理，由主代理判断。

## 任务依赖、职责和执行配置

确实决定分工时，读取 [代理任务约定与机队路由](references/delegation.md)，然后：

- 先识别依赖：未确定的共享接口、数据模型和验收标准应先解决，不能通过并行写代码掩盖。
- 每个子任务限定写入所有权。对实际共享目录和独立 worktree 作出区分，检查工具行为，不假定它们天然隔离。
- 角色根据本次问题形成，例如“定位重复扣减的调用路径”，而非固定要求每项需求都配架构师、实现者、测试者。
- 用 Agent 工具派发，显式传入 `subagent_type`：只读调查与状态核实用 `orch-scout`，限定范围内的实现用 `orch-builder`，基于原始证据的独立审查用 `orch-auditor`；无匹配机队角色时用内置 `Explore`（只读调查）或 `general-purpose`（需要写入或多步执行），渲染交付物的视觉验收用 `judge`。模型档位固化在机队卡片上，派发调用没有模型参数，不虚构字段。
- 启动前形成一行记录：`角色 → 子代理类型 → 选择原因`；最终报告如实记录实际派发的类型，不把计划中的派发当成已经发生的派发。
- 每次派发都是全新会话，任务消息必须自包含最小充分背景；需要追加追问时用 SendMessage 恢复原子代理，不重新派发。
- 机队卡片缺失时（换机器或被删除），按 [代理任务约定与机队路由](references/delegation.md) 的规格重建，下个会话生效；当前会话改用内置类型，不为等待铸造而阻塞已授权任务。
- 本技能只约定已授权任务内的分工和路由选择，不授予新的数据访问、外部发送、付费购买或发布权限。

## 执行、验收和结束

- 子代理运行时推进主代理的独立工作。不要重复实现已委派的任务，或把未返回的推测当作结果。
- 阅读子代理的实际差异与证据，对重要结论检查原始代码、测试或日志。独立审查先获得任务目标、约束和原始材料，不先获得期望结论。
- 按验收标准、改动范围和项目已有要求验证；不要求所有改动都运行完整测试集。记录未运行、失败和环境阻碍。最终验证必须对应最终相关代码状态。
- 在检查点执行会话协议；只在有意义的节点更新持久状态，不写聊天流水账。
- 最终报告说明结果、验证、剩余事项，以及“继续 / 建议交接 / 先解决阻塞”的决定和依据。没有实际创建子代理或运行测试时不得声称已执行。
- 工具不可用、配额不足或不能并行时，切换单代理执行可完成的部分并说明限制；不得把文本角色扮演描述成真实的多代理运行。
