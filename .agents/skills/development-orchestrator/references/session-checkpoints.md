# 会话检查与交接

目标：由代理发起有证据的检查并给出交接决定，用户不必诊断模型是否已经混乱。该协议在代理执行任务时生效，不是后台监视器，不承诺检测所有偏差。

## 一、确定可验收的任务单元

新会话开始定义本次任务单元：目标、验收、范围、关键约束。优先复用已有目标与工作状态。一个任务单元是有用户可观察结果的一项功能、修复或阶段交付，不把读文件、跑命令、子代理子步骤分别计数，也不把整个长期项目作为一个无限任务。必需验收项未通过或未执行时，不计为验收完成；分别记录实现完成、验收完成和环境阻塞。

在已有 STATE 中追加或整理一个短检查区；无状态文件且任务确需长期接续时创建 `docs/ai/STATE.md`，小任务无需建立整套资料。

```text
会话标识：可获得的任务 ID，或本地自定的日期与简短标识
本次目标与验收：
开始/最近检查的代码基线：
已完成任务单元：0
最近检查点：时间、触发原因
G 目标对齐：PASS / FAIL / UNKNOWN，证据位置
R 实现状态：PASS / FAIL / UNKNOWN，基线及工作区差异
C 约束与决策：PASS / FAIL / UNKNOWN，依据或冲突
V 验证对应性：PASS / FAIL / UNKNOWN，结果对应的代码状态
N 下一步：PASS / FAIL / UNKNOWN，具体行动及其前置条件
发现/核实/未解决：
决定：继续 / 准备交接 / 暂停相关修改并处理阻塞
交接建议原因与下一会话入口：
```

用户更新目标时记录变化，再重新确定范围；不能让旧目标压过用户当前明确指令。仓库基线用实际 Git 与工作区状态核实，不只记录已提交内容。工具或环境不可见的状态写 UNKNOWN。

## 二、何时必须检查

- 新开发会话接手任务，或恢复执行时已经明确观察到上下文压缩/恢复提示。
- 开始新的有实质影响需求；架构、公共接口、数据模型或兼容策略即将改变。
- 完成一个可验收任务单元，或集成有实质影响的子代理结果。
- 实际出现矛盾：文件/接口与描述不符、重新采用曾否决方案却未说明新依据、未经说明扩大范围、把旧检查当作新代码的验证。
- 相同失败在没有新证据或新假设的情况下再次出现：先重新调查，不能自动认定为上下文故障。

检查发生在工作边界，不是每条消息或每次工具调用后。没有客观压缩信息时，不猜测压缩次数。

## 三、如何检查

G：把当前计划和 diff 对照本次目标与验收标准。必要支持性修改可接受；发现无关扩展时说明并收敛，不能自动删除用户改动。

R：核实仓库、分支、HEAD、暂存/未暂存/未跟踪文件，再定向读取关键实现。实际存在的代码与“已实现”的声明不一致时报告具体差异。

C：检查本次涉及的约束、接口契约和必要 ADR；找不到原因时标记缺失。旧决策允许被新事实替代，但应明确新事实与替代记录。

V：核对实际运行结果、测试覆盖的行为和对应的代码状态。尚在实施时“明确记录未测试”不等于会话失效；完成任务时缺少验收证据必须保留“未验证”。测试失败本身也不等于上下文失效。

N：说明下一步具体动作和前置条件；无法说明时先定位缺少的是代码事实、需求决定还是外部条件。

PASS 必须有依据，UNKNOWN 不能当作 PASS。检查只覆盖当前任务涉及的约束，不做常规全仓审计。

## 四、判断与行动

1. **证据一致：继续。** 正常开发。完成节点可报告“会话检查：可以继续；状态已对齐，下一步是……”。这仅表示已检查项一致，不宣称对话绝不会跑偏。
2. **发现可定位偏差：先修复认知。** 暂停依赖偏差的修改，定向重读原始资料和代码，修正过期状态，再复核一次。恢复一致后继续，不必换会话。
3. **仍有实质矛盾：停止猜测。** 若主代理仍无法稳定解释可获取的材料，或核实后再次沿同一错误假设行动，建议交接；保存事实和未知，不再扩大依赖不确定信息的实现。材料足够且确有独立价值时，请只读子代理根据任务约定、实际差异和原始文件独立核查，不要求其证明主代理正确。
4. **缺的是需求、权限、依赖服务或环境：处理阻塞。** 清楚指出需要哪个决定/条件，继续不依赖它的工作。换对话不能代替补齐这些信息，不把外部阻塞包装成“上下文坏了”。

修复认知的一轮核实应围绕具体矛盾，而非无限次自我检查。若无法找到证据，在交接资料中保留 UNKNOWN；不能制造绿色状态。

## 五、不依赖故障判断的预防性交接

默认以一个阶段目标完成作为自然交接点。用户在同一会话继续提出新开发任务时，每完成三个有验收结果的任务单元，主动整理交接并建议下一项开发在新会话开始。只统计当前会话中持久状态可核实的任务单元；历史计数丢失时重新建立检查点，不编造累计数量。

“三个”是可调整的初始维护周期，不是模型上下文的科学阈值。用户可以调整为一个阶段一次或其他周期。达到周期时先完成安全的当前边界，不放弃正在推进的已授权任务；提醒用户后，不替用户创建新任务，除非用户已经明确要求这样做。预防性建议不构成新的批准门槛；如果用户已经提出下一项任务，未明确要求暂停或切换时，继续已授权工作，不等待重复批准。用户决定继续当前会话时保留检查与状态写回，不反复重复同一提醒；下一次新的实质风险仍需提示。

在一个很长但尚未完成的任务中，依靠第二节的实施检查点发现偏差；周期计数不代替这些检查。

## 六、交接交付与接手验收

协调正在写入的代理到稳定边界，记录实际工作区。更新唯一有效的 STATE 与必要决策资料；记录已实现、已验证、未完成和未知，保存复现步骤、尝试结果与不应重试的原因。只保留有价值的事实和路径。

提出交接时直接告诉用户：

```text
建议下一项开发切换到新对话。
触发原因：具体证据，或预防性交接周期。
当前停点：实现与验证到了哪里。
已保存：状态文件、代码基线、工作区变更、未解决问题。
下一会话：读取哪些入口，先完成哪一个动作，怎样验收。
```

新会话从项目状态和原始证据恢复目标、范围、关键约束、当前实现和下一步，再推进。不能把旧聊天复制一遍或继承旧历史等同于获得清晰上下文。若缺少项目资料、文件或真实基线，先说明接手所缺信息。

用实际结果验收交接：新会话能准确复述当前任务与依据、找到实现位置、知道哪些尚未验证，并提出正确的第一步。独立核查可以降低同一错误持续传播的风险，不能保证发现所有错误。
